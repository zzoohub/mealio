# Software Architecture Documentation

## Overview

Mealio is a photo-first meal tracking application built as a monorepo with two primary components: a Rust/Axum REST API backend and a React Native/Expo mobile frontend. The system follows a dual-mode architecture where authenticated users interact with a PostgreSQL-backed API (Neon) while guest users operate entirely on-device via MMKV local storage. All photo storage is handled through Cloudflare R2 via presigned URLs, and the API is deployed on GCP Cloud Run as a containerized Knative service.

### API Feature Modules

#### Auth (`/api/src/features/auth/`)

- **Purpose**: OAuth sign-in (Google, Apple), JWT access/refresh token management with rotation and reuse detection.
- **Submodules**: `handlers.rs`, `models.rs`, `router.rs`, `jwt.rs`, `jwks.rs`, `oauth.rs`.
- **Key Behavior**:
  - Sign-in: Verify ID token via JWKS (RS256) -> find-or-create user in transaction -> issue JWT access token (15 min) + refresh token (30 days, blake3-hashed in DB).
  - Refresh: Validate hash, rotate tokens (revoke old, issue new). Implements **reuse detection**: if a revoked token is reused, all tokens for that user are revoked.
  - Revoke: Requires auth; validates token ownership before revoking.
  - Soft-deleted users are **restored** on re-login.
- **Routes** (nested under `/api/v1/auth`):
  - `POST /sign-in` -- OAuth sign-in
  - `POST /refresh` -- Token refresh with rotation
  - `POST /revoke` -- Token revocation (auth required)
- **Location**: `/Users/zzoo/apps/mealio/api/src/features/auth/`

- **Soft deletes**: `users.deleted_at`, `diary_entries.deleted_at` -- records remain but are filtered by `WHERE deleted_at IS NULL`.

## Data Flow

### 1. Meal Capture and Photo Upload Flow (Authenticated)

```
Mobile App                    Mealio API               Cloudflare R2        Neon PostgreSQL
    |                             |                         |                    |
    |-- (1) Capture photo ------->|                         |                    |
    |   (expo-camera/image-picker)|                         |                    |
    |                             |                         |                    |
    |-- (2) POST /uploads/presign |                         |                    |
    |   { content_type }          |                         |                    |
    |<---- { upload_url,       ---|                         |                    |
    |        object_key,          |                         |                    |
    |        public_url }         |                         |                    |
    |                             |                         |                    |
    |-- (3) PUT upload_url -------|------- direct --------->|                    |
    |   (binary photo blob)       |                         | (store object)     |
    |                             |                         |                    |
    |-- (4) POST /diary --------->|                         |                    |
    |   { meal_type, notes,       |-- INSERT diary_entry -->|                    |
    |     eaten_at, location? }   |                         |                    |
    |<---- { entry } -------------|                         |                    |
    |                             |                         |                    |
    |-- (5) POST /diary/{id}/photos ->|                     |                    |
    |   { url: public_url,        |-- INSERT entry_photo -->|                    |
    |     is_primary: true }      |                         |                    |
    |<---- { photo } -------------|                         |                    |
```

**Steps:**
1. User captures or selects a photo using `expo-camera` or `expo-image-picker`.
2. Mobile app calls `POST /api/v1/uploads/presign` with the detected content type. API validates content type (jpeg/png/webp/heic only), generates a unique object key `photos/{user_id}/{uuid}.{ext}`, creates a presigned PUT URL (15-minute expiry) via AWS S3 SDK against R2, and returns the upload URL, object key, and public URL.
3. Mobile app uploads the raw photo blob directly to R2 using the presigned URL (client-side upload, no API proxy).
4. Mobile app creates the diary entry via `POST /api/v1/diary` with meal metadata. If location data is available (from `expo-location`), it is included inline.
5. Mobile app attaches the photo record via `POST /api/v1/diary/{id}/photos` with the R2 public URL.

### 2. Authentication Flow (OAuth + JWT)

```
Mobile App           Google/Apple IDP         Mealio API            PostgreSQL
    |                      |                      |                     |
    |-- (1) OAuth sign-in ->|                      |                     |
    |<-- ID token ----------|                      |                     |
    |                       |                      |                     |
    |-- (2) POST /auth/sign-in ------------------->|                     |
    |   { provider, id_token, device_info }        |                     |
    |                       |                      |                     |
    |                       |  (3) Decode header,  |                     |
    |                       |      extract kid     |                     |
    |                       |<---- GET JWKS -------|                     |
    |                       |---- JWKS keys ------>|                     |
    |                       |                      |                     |
    |                       |  (4) Verify RS256    |                     |
    |                       |      Check aud, iss  |                     |
    |                       |                      |                     |
    |                       |            (5) BEGIN TX                    |
    |                       |            Find or create user ----------->|
    |                       |            Create auth_token (blake3) ---->|
    |                       |            COMMIT TX                      |
    |                       |                      |                     |
    |<-- (6) { access_token (JWT 15min),           |                     |
    |         refresh_token (UUID 30day),           |                     |
    |         user } --------------------------------|                     |
    |                       |                      |                     |
    | (7) Store tokens:     |                      |                     |
    |   access -> SecureStore (keychain)           |                     |
    |   refresh -> SecureStore (keychain)           |                     |
    |   expiresAt -> MMKV (sync)                   |                     |
    |   user -> MMKV (offline hydration)           |                     |
```

**Steps:**
1. User initiates OAuth via Google Sign-In SDK or Apple Authentication SDK on the mobile device.
2. Mobile sends the provider's ID token to `POST /api/v1/auth/sign-in`.
3. API decodes the JWT header to extract the `kid` (key ID), then fetches (or retrieves from cache) the JWKS from the provider's endpoint.
4. API verifies the ID token signature (RS256 only, hardcoded algorithm), validates audience (Google client ID or Apple bundle ID) and issuer.
5. Within a database transaction: looks up `user_auth_providers` by provider+provider_uid; if not found, creates a new `users` record and `user_auth_providers` link; if the user was soft-deleted, restores them. Creates a new `auth_tokens` record with blake3-hashed refresh token (30-day expiry).
6. Returns JWT access token (HMAC-SHA256, 15-minute expiry, UUID v4 JTI) and plain-text refresh token.
7. Mobile stores tokens: sensitive tokens in `expo-secure-store` (encrypted keychain/keystore), expiry timestamp in MMKV for synchronous access, user data in MMKV for offline hydration.

**Token Refresh:** The API implements **refresh token rotation with reuse detection**. On refresh, the old token is revoked and a new one issued. If a previously revoked token is presented, all tokens for that user are revoked (family revocation), indicating a possible token theft.

## Technical Debt / Concerns

1. **AI Analysis Not Implemented**: The `POST /api/v1/diary/{entry_id}/analysis` endpoint returns `501 Not Implemented`. The mobile `AIAnalysis` type and `GUEST_LIMITS.AI_ANALYSIS_ENABLED` flag exist, but no AI integration (LLM or vision model) is wired up. The database schema stores a `raw_response JSONB` field anticipating an external AI service response.

2. **No CI/CD Pipeline Detected**: No GitHub Actions workflows, Cloud Build configs, or other CI/CD manifests were found in the repository. Deployment appears to be manual (`docker build` + `gcloud run services replace`).

3. **CORS Configuration**: In development, CORS is fully permissive (`CorsLayer::permissive()`). Production restricts origins via `CORS_ORIGINS` env var, but this env var is not present in `service.yaml`, suggesting it may default to permissive in production as well.

4. **No Rate Limiting**: The API has no rate limiting middleware. Combined with scale-to-zero (0 minimum instances), this could lead to abuse during cold start periods.

5. **SQL Injection via ORDER BY**: The diary list query uses string interpolation for `ORDER BY` clause (`format!("ORDER BY {}", order_by.to_sql())`). While the enum-to-SQL mapping is hardcoded and safe, this pattern circumvents SQLx compile-time query checking for that portion.

6. **Token Expiry Synchronization**: The mobile token store uses MMKV for the `expiresAt` timestamp (synchronous reads) but SecureStore for the tokens themselves (asynchronous reads). There is a brief window during `loadFromStorage` where the expiry is known but tokens are not yet loaded, though this is handled gracefully by requiring both to be present.

7. **Guest Entry Migration is Simplistic**: The `useMigration` hook uploads entries sequentially without retry logic or progress tracking. If the migration fails partway, some entries will exist on the server and all will still exist locally, with no deduplication mechanism.

8. **No API Versioning Strategy Beyond v1**: All routes are under `/api/v1` but there is no documented strategy for v2 migration or backward compatibility.

9. **Photo Cleanup Orphans**: When a diary entry is soft-deleted, the associated R2 objects are not cleaned up. Photo records cascade-delete in the database (on hard delete), but R2 objects persist indefinitely.

10. **Offline/Queue Support Incomplete**: The `Entry._uploadStatus` field suggests an upload queue was planned, and a `guestEntryStore` bump pattern exists, but there is no background upload queue or retry mechanism for failed uploads in authenticated mode.
